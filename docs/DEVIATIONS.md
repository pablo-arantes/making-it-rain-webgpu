# Deviations

Every place the web app does something the notebook does not. The rule from
`AGENTS.md` is that physics never changes silently: each entry says what the
notebook does, what the app does, why, and whether the user is told.

"Shown" means the UI states it at the point where it matters — not buried in a
tooltip — and that `run.json` records it so a run can be reproduced in either
place.

| 14 | Mixed precision keeps velocities in `float4` and masses in single | The same: velocities and inverse masses in f32 | The format a quantity needs is set by the ratio of its value to its increment. | 15 | Langevin noise comes from OpenMM's own generator, in its own order | Threefry-2x32-20 (Random123), counter-based on (particle, axis, step, seed) | OpenMM's stream cannot be reproduced: its GPU platforms draw in their own order, and two Langevin trajectories from different noise diverge however exact each step is. | 16 | `Modeller.addHydrogens` places each new hydrogen at its parent plus a 0.1 nm offset built from `random.random()`, then energy-minimises the whole set | The same hydrogens, with positions chosen deterministically: 0.1 nm from the parent, in the direction that maximises the smallest angle to the bonds the parent already has. | 17 | A neutral histidine is documented as taking HID or HIE "based on which one forms a better hydrogen bond" | Always HID | 🔴 Not a choice. OpenMM's rule is unreachable: `_addHydrogens` initialises `nd1IsBonded` and `ne2IsBonded`, and the loop meant to test NE2 assigns `nd1IsBonded` a second time. `ne2IsBonded` is never set, so `if ne2IsBonded and not nd1IsBonded` cannot fire and the automatic path always returns HID. Selecting HIE where the geometry favours it would be defensible chemistry and a silent disagreement with the oracle on every neutral histidine — and histidine's charges differ between the two. Until all of it exists, silently substituting a cube would change the density and the cost of a run | yes — the refusal names the shape and says why |

## Not deviations, but worth stating

* **Bitwise agreement across devices is not promised.** Within one device, one
  seed and one workgroup configuration, a run is bit-identical; across GPUs it
  is not, because the kernels are allowed to pick different workgroup shapes.
* **Single precision is the forces' precision.** The engine targets OpenMM's
  mixed-precision behaviour, not its double-precision Reference platform. The
  measured floor for a legitimate single-precision implementation is ~1e-5
  relative force error — OpenMM's own OpenCL platform sits at 1.05e-05 on an
  equilibrated 1L2Y.
* **The notebook remains the oracle.** Anything in this file that turns out to
  change a scientific result, rather than a label or a reproducibility
  property, is a bug in this file's reasoning and should be raised.
